# inkweave-admin

Private admin tools for Inkweave. The public app is `Doberjohn/inkweave`, served at inkweave.ink. Design, plan and phase status: [docs/PLAN.md](docs/PLAN.md).

## How this repo relates to the app

- `upstream/inkweave` is the app repo as a git submodule, **pinned** to one commit and **read-only here** (a hook blocks edits). App changes go through the app repo; admin then bumps the pin. Never run `pnpm install` inside `upstream/`: a second `node_modules` there would give bridged files a second React.
- `src/app-bridge.ts` is the **only** source file that may import from `upstream/` (lint-enforced; the one exception is `eslint.config.js`, which loads the app's design-token plugin). Add re-exports there; never deep-import app files anywhere else. It also re-exports the app's promo merge (`mergePromoPrintings`, `collectionPromos`, `finishesById`, `byPrintingOrder`) and its check of a promo's card (`promoBaseProblems`) from `upstream/inkweave/scripts/lib/*.mjs`, typed in the bridge itself, since `tsconfig.app.json`'s `allowJs` lets it import that plain JavaScript. `scripts/browser-safety.test.mjs` fails when anything `src/main.tsx` or a story loads imports a Node builtin: Vite only warns, and the page then fails to load.
- Admin writes into the app repo **only through the GitHub API**: the tools commit to `master`, and reveal ingestion opens PRs. Never write into a local app checkout.
- The engine (`inkweave-synergy-engine`) is a pnpm workspace package built from the submodule (`pnpm build:engine`). `typecheck`, `build` and `test:run` build it themselves; run it once before `pnpm dev` on a fresh clone or after a pin bump.
- Admin declares the app's full runtime dependency set at the app's exact versions. `pnpm check:deps` verifies this, and `pnpm check:deps --fix` aligns it.

## The tools

- `src/tools/studio` holds Card studio, over `src/tools/reveal`'s write chain and controller (reveal-sync loads the chain by path, so it stays put) and `src/tools/image`'s `filterCards` and `commitCardImage`; `src/tools/changes` holds Change history; `src/tools/analytics` holds the insights pages, `src/tools/tuning` the tuning editor's hooks, GitHub client, tray and tier row (the editor itself is `/calibration`'s aside, `analytics/calibration/TuningAside`), `src/github/` the GitHub read/write layer, `src/theme/` and `src/ui/` admin's theme and UI primitives, `src/charts/` the chart kit, and `src/shell/` the layout every route renders in: a collapsible sidebar, which remembers its state per browser, and `PageLayout`, the header every page renders through. The kit is hand-built SVG on the admin theme, with no chart library, and every new chart builds on it: bar, line and scatter charts, and since R3 the synergy `NetworkDiagram`. `Sparkline`, `MeterBar`, `SplitMeter` and `BiasBar` stay `src/ui` primitives: small marks beside numbers the page prints, not charts. A new chart follows the `dataviz` skill's guidance (its mark specs, one tooltip that the keyboard reaches too, a Chart | Table toggle, one y axis) and the redesign's chart decisions, R-9 and R-12 to R-15. Where they differ, the decisions win: R-14 keeps the display face on headline numbers and R-15 keeps the brand colours. How the tools were ported: [docs/plans/P2-port-tools.md](docs/plans/P2-port-tools.md). The redesign, phase by phase: [docs/plans/R-redesign.md](docs/plans/R-redesign.md).
- The layers under the tools never import them: no module in `src/shell`, `src/ui`, `src/charts` or `src/theme` imports from `src/tools` (R-53), and `src/ui` doesn't import the chart kit, which builds on it. Stories and tests may. `eslint.config.js` enforces both. It also fails on any function the React Compiler would skip, in every non-test file under `src/` (`react-hooks/todo` and its siblings): the compiler skips one silently, leaving it unmemoized under the `useMemo` ban. So never write `try … finally` in a component or hook (#59). A page whose controls take a dropped file (`src/components/useFileDrop.ts`) also mounts `useFileDropGuard`, as `/studio` does, so a file dropped beside them never opens in the tab.
- Routes: the Overview at `/`, the insights pages `/calibration`, `/activity`, `/web` and `/cards/:cardId?` (Card analytics), the write tool `/studio` (Card studio: New reveal, and Edit card at `?mode=edit&card=<id>`; a mode switch keeps `?card=`), and `/changes` (Change history). `/calibration` writes too: its aside is the tuning editor. `/changes` only reads: every commit on the target branch that changed the preview cards, raw scans, card data or `tuning.json` (`changePaths.ts`), each followed path's history read a page at a time through `src/github/githubHistory.ts` and merged into one list, convert-reveal-images' commits left out. A change opens onto what its commit did, read from the commit itself once a session (`commitDetails`): card fields in Edit card's words, printings' versions in the Printings panel's, tuning values, and the scans. `src/shell/nav.ts` lists the sidebar's items, marks the ones that write (`writes`) and builds the links into pages (`calibrationHref`, `cardsHref`, `studioHref`). `/cards/:cardId` shows one card, and a bare `/cards` opens the last card viewed, which each browser remembers (`cards/lastCard.ts`), or a "Pick a card" prompt. Card names on the other insights pages link to `/cards` only through `CardName`, `PairNames` or `PairLine` (`src/tools/analytics/CardName.tsx`), for ids the card list holds (`KnownCardsContext`, R-33): AdminShell's `KnownCardsProvider` fills it, and its default links nothing, so a view's tests and stories need no card list. Every link that is a card's name, these and Card analytics' Voted pairs and Cards to review, and Change history's card and printing names, is a `CardLink` (`src/shell/CardLink.tsx`): it shows the card's art, or a printing's own, beside the name while the pointer rests on it or the keyboard focuses it (`src/ui/ArtLink.tsx`), from `CardArtContext`, which `KnownCardsProvider` fills from the card list too. Its default has no art, so outside the shell the link is plain; `src/test/cardLinks.tsx` gives tests both contexts. The network's Table view is the chart kit's own table, so its card names are `ArtLink`s, which `partnerTable` hands the same art (`ChartTableLink.art`). The open card's id (`src/ui/CardId.tsx`) shows in Card analytics' header and Edit card's banner. `src/router.tsx` also redirects retired paths: `/analytics` goes to `/`, `/tuning` to `/calibration`, `/reveal` to `/studio`, and `/image` to `/studio?mode=edit`. The insights pages read `/admin-data/` only through `fetchAdminData`, which keeps each file's promise for the session (`src/test/setup.ts` empties it before every test). `/calibration` and `/cards` share one votes filter (#33, `src/tools/analytics/votesFilter.ts`), held in memory for the session: `src/test/setup.ts` and `.storybook/preview.tsx` put it back to Any before every test and story. `/cards` also reads each card's synergy file from the forwarded `/data/synergies/` through the bridged `fetchCardSynergies`, whose cache no test can empty, so tests mock it through the bridge, or give each case an id no other test fetches.
- Card studio and the tuning editor commit to `Doberjohn/inkweave` on `VITE_ADMIN_TARGET_BRANCH`, which defaults to `master`, and read the files they edit (`previewCards.json`, `tuning.json`) from that branch. A commit that would change nothing is refused: `commitFiles` makes none, and the branch stays where it was. Card studio reads `previewCards.json` for Edit card when it opens and after each of its commits that changes the file, and each such commit reads it again at its base, as an image-only save of a preview card (any card under a preview id) does to check the card is still there. Card lists come from `inkweave.ink` through the forwarded `/data/`, so Edit card's search adds the cards only the branch's `previewCards.json` holds, tagged "not deployed yet" (R-66). Edit card's Printings panel sets a released printing's versions (`finishes`, #68; [docs/printing-finishes-design.md](docs/printing-finishes-design.md)), and reads their values from the branch's `allCards.json`, `collection/{set}.json`, `collection/promos.json` and promo catalog. A Sets 1 to 8 card, which only the deployed `/data/collection/1.json` to `8.json` hold, is found by the search and opens printings-only: no image control and no Save. Version changes don't save per card: they collect in the studio-wide Version changes tray, which keeps them in `localStorage` per target branch, and its Publish writes them in one commit into every one of those files that holds each printing, each in its own format; a file whose text isn't in its format is refused, naming the file, before anything is written. A printing whose value in its primary home changed on the branch since its change was staged is a clash: the change stays in the tray, holding Publish, until the owner keeps or drops it. New reveal checks a collector number against inkweave.ink's card list, so its Publish stays off until the list has loaded without error. To rehearse writes, create a throwaway branch in the app repo and set the variable in `.env.local` (`.env.example` has the line). Every page that writes names the branch in its header (`BranchNotice`, from `targetBranch()`), and read-only pages don't. A new write page sets `writes: true` in `nav.ts` (the sidebar's token box, through `isWritePath`) and passes `writes` to its `PageLayout` (the branch notice).
- Edit card's Printings panel also adds and edits a released card's promo printings (#77; [docs/promo-printings-design.md](docs/promo-printings-design.md); the code is `src/tools/studio/promos/`). Add a printing under the rows opens a form for a new one, and Edit on a promo row opens its form filled in from the branch's catalog. One form is open at a time, and `StudioWorkspace` holds it through `usePrintingForm`, so a mode switch keeps it. Each publish is one commit of its own: it never takes the card's own save or the Version changes tray with it, and theirs never take the form. The line under the rows says what the last one came to, and keeps its commit in view even when the read of the branch after it fails. It writes the app's promo catalog (`scripts/data/promo-printings.json`: the entry; a provisional id's line in `provisionalIds`, which a printing under a LorcanaJSON id doesn't have; a note; and the recounted `stats`, any count admin doesn't know kept as it is); `allCards.json` and `collection/promos.json` as the app's own promo merge, bridged, writes them over the commit's base files (admin never edits their entries itself, and sends a file only when the merge changes it: `allCards.json`'s text, or `promos.json` hash keys aside, as the app's CLI reads it); and the scan, when there is one, to `card-images-raw/{id}.{ext}`, which the app's convert workflow turns into art on master only, so on a throwaway branch the data lands and the art doesn't. An add takes the next provisional id, one above the highest in `provisionalIds` or among the entries (a provisional printing can lack its line); a printing removed by hand keeps its line there, marked "(removed)", so an id is never issued twice. An edit changes a promo's set, number, scan language and scan, and adds a note, but never its id, so the copies players counted stay with it; it replaces the scan only where the printing has no Ravensburger art (`images` in its catalog entry). A publish is refused, writing nothing, when the branch's catalog and card files are out of step (the app's merge over them would change something, `promos.json` compared the same way: run `pnpm merge-promos --write` there), when an edited printing changed on the branch since its form opened (only then is the form re-seeded, with the branch's values and the note the owner typed) or is gone from it, or filed under another card since (the form closes, and the line under the rows says so), when the promo set isn't one the app knows (an edit is checked only if it changes its set), when another printing has the code (an edit is checked only if it changes its set or number, since twins such as the two 26/P2 printings already share one), or when an add starts a Sets 1 to 8 card's group and the app's data for its set on the branch lacks the card or names its id otherwise (the app's `promoBaseProblems`, bridged, over the new printing). A catalog missing a section also fails a promo publish, writing nothing. The panel reads the catalog through the same check, but only the printing form depends on it: the panel keeps its rows, whose versions stage as ever, and the message, which names the file and the section, stands in place of Add a printing and every Edit (#84). A publish also refuses a catalog whose text isn't in its format (`JSON.stringify(x, null, 2)`, no newline at the end), naming the file and its format, so it never rewrites all of it; the panel still reads such a catalog. The form offers `PROMO_SETS` at the pin, and says under its select that a set it lacks needs the app first: a new promo set is an app change and then a pin bump. A Sets 1 to 8 copy of a card that a Core card reprints offers no Add a printing: the catalog files the card's promos under the Core card, so its panel links there.
- Write pages sit behind `GithubTokenGate`; on `/calibration` only the tuning aside does, so the analytics need no token. `/changes` writes nothing but sits behind it too, since the app repo is private. `useGithubToken` is one store shared by every component, so the sidebar's token box (on write pages, once a token is saved) and its "Forget token" act on every page at once. On `/studio` that drops every draft without asking: they live under the gate, in a workspace keyed by the token. The page's own Forget token, offered when GitHub rejects the token, asks first while a draft is dirty (R-84), naming each dirty one, the printing form's too. A page that holds unsaved edits mounts one `UnsavedChangesGuard` (`src/shell/`), which asks before leaving it: `/calibration` and `/studio` do. The studio's guard leaves the Version changes tray out: its batch lives in the browser, so leaving loses nothing. It counts three drafts: New reveal's, Edit card's, and the promo printing form's (#77). By default only a new pathname leaves; a page whose search names what it edits passes its own `leaves`: the studio's (`shouldBlockStudioNavigation`) also asks when `?card=` changes, and never on a mode switch, since every draft stays mounted. `message` may be a function of where the held navigation goes, so the studio names only the drafts that navigation would drop: a card change drops Edit's draft and the printing form, which belong to the card, and never New reveal's. A page may also word the dialog itself: the function may return a whole `UnsavedQuestion`, its title and answers with its line, which the guard hands `UnsavedChangesDialog` as `words`. The studio does for a held card change, which stays on the page: "Leave this card?", with "Keep editing" and "Drop changes", or "Leave the card" when each draft the change drops is held by its own save or publish (it landed, so the change drops nothing, or it is still in flight); a draft beside it with no commit in flight is dropped outright, so then the answer is "Drop changes". Both pages word a publish or save still in flight through `writeInFlightMessage` (`src/shell/writeInFlight.ts`). The studio words New reveal's publish, and the printing form's, so in either mode (that form is held while its publish runs, so its line adds nothing), and Edit card's save only when it was made from the draft on screen, adding what leaving still drops: edits made since the save started (the form stays editable while it runs), and the save's own if it fails. The guard needs the data router, so tests render a guarded page with `createMemoryRouter`, never the `MemoryRouter` wrapper. When an action unmounts the control that had focus (Save token, Retry, a link to the next card), the page hands focus to the next view through `src/shell/focusHandoff.ts`, and never moves it otherwise (R-48). A router link never requests the handoff in its click handler: React Router renders the navigation as a transition, so the old view, still mounted, would take the request first. The page requests it from its state instead: when the URL names another card, except on a REPLACE, which is no one's action, or when its data's error clears (`/cards`, R3-7; the studio's Edit card, R-59). Two more shell helpers hold the other focus rules, so no page writes its own: `src/shell/rowFocus.ts`, the one rule for a list whose row goes with the button pressed, and `src/shell/clearBand.ts`, which keeps a focused control clear of a box pinned over the page (the tuning aside's header and tray, and the Version changes tray's foot, which the studio keeps clear for keyboard focus only).
- Admin enables the app's design-token rules by name in `eslint.config.js`, every one of them. Admin files pass the rules it enables with no exception. Admin's palette and scales live in `src/theme/adminTheme.ts` (`ADMIN_COLORS`, `ADMIN_TYPE`, `ADMIN_RADIUS`, `ADMIN_LAYOUT`), composed only from bridged tokens: add a value there, never a literal in a component. Hover, focus, selected and drag-over states come from one scoped stylesheet, `src/theme/AdminStyles.tsx` (`adm-*` classes), whose rules interpolate the same tokens. Data text is never `COLORS.textDim`, which fails contrast on these surfaces, and mono text is a bare `<code>`. Buttons are the app's kit through the bridge (`CtaButton`, `LinkButton`) or a native `<button className="adm-…">`, never a styled `<button>`.

## Pipelines

- **Analytics.** The Deploy workflow runs nightly (04:00 UTC), on every push to `main`, and on demand (`gh workflow run deploy.yml --repo Doberjohn/inkweave-admin`). It checks out the app's `master` into `app-master/`, builds that engine and its synergy data, and runs `scripts/precompute-{vote,vercel}-analytics.mjs`. Those write `public/admin-data/`, which ships inside the login-gated deployment. `app-master/` and `public/admin-data/` are git-ignored; locally the insights pages show their "not generated" state. To see real data locally, the owner saves the deployment's three `/admin-data/` files into `public/admin-data/` ("Seeing R1 with real data locally" in [docs/plans/R-redesign.md](docs/plans/R-redesign.md)); never commit them. How it was built: [docs/plans/P3-pipelines.md](docs/plans/P3-pipelines.md).
- **Reveal ingestion.** `/fetch-reveals` runs from an admin session (`.claude/skills/fetch-reveals/`, `scripts/reveal-sync/`). Its `write` opens a PR in the app from a `reveals/…` branch and commits `scripts/reveal-sync/state.json` straight to `main`; CI and Deploy skip a push that changes only that file. It reads the season through `src/app-bridge.ts`, so bump the pin when the app rotates the season. Runbook: [docs/REVEAL_RUNBOOK.md](docs/REVEAL_RUNBOOK.md).
- **Variant printings.** Epic, Enchanted and Iconic printings are never cards. `node scripts/reveal-sync/variants.mjs stage <numbers>` checks and stages them, and `publish <run>`, run only once the owner approves, opens a `reveals/set<N>-variants-…` PR in the app. It never writes `state.json`. Runbook: "Variant printings from admin".
- **Errors.** Production builds report errors to Sentry's `inkweave-admin` project (org `fanidis-ioannis-lp`, EU region), set up as the app's is except that `src/sentry.ts` starts Sentry first (main.tsx imports it before anything else) rather than after `load`. It also hands `createRoot` the hooks that report what React catches, React Router's error screen included. Deploy's Build step passes `VITE_SENTRY_DSN`, which turns it on, and `SENTRY_AUTH_TOKEN`, with which `vite.config.ts` uploads hidden source maps and then deletes them, only when the DSN is set too. A build without the DSN has neither, so dev, tests and CI never report.
- **Reviews.** `.github/workflows/claude-review.yml` (#91) has Claude Code review a pull request when it opens ready for review and when a draft is marked ready, never on a push: the bundled `/code-review` skill, at `high` effort on Opus, posts its findings as inline comments from `github-actions[bot]`, and it checks out the pinned app so the review can read what the bridge re-exports. A top-level comment starting `@claude review` on an open PR, from someone with write access, asks for another pass. Drafts and Dependabot's PRs get no automatic review, and forks get none at all. The job's token only reads code and writes PR comments, and the run turns off `.claude/hooks`. Claude's shell commands run in a sandbox that holds neither the API key nor the token, so the review reads the diff with git, never `gh`. A failed review run is advisory: nothing waits on it.
- **Secrets.** `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `VERCEL_ANALYTICS_TOKEN` and `ANALYTICS_VERCEL_PROJECT_ID` (the app's Vercel project: in the workflow, `VERCEL_PROJECT_ID` names admin's own), plus Sentry's `VITE_SENTRY_DSN` and `SENTRY_AUTH_TOKEN`, and `ANTHROPIC_API_KEY` for Claude's reviews (a Claude Console key in a workspace that caps the monthly spend). The owner sets them.
- **Logs.** The precomputes log the files they write, never vote, voter or event counts: a public repo's workflow logs are public.

## Commands

```bash
pnpm dev              # http://localhost:5180 (the app uses 5173-5175)
pnpm build            # engine + tsc -b + vite build
pnpm typecheck        # engine + tsc -b (includes every bridged app module)
pnpm lint
pnpm test             # vitest watch; pnpm test:run for one pass (builds the engine first)
pnpm check:deps       # dependency parity with the pinned app
pnpm check:hooks      # the .claude/hooks case table (CI runs it; minutes on Windows)
pnpm storybook        # http://localhost:6007: the shell, pages, primitives, charts and tools
```

Vitest runs two projects (`vite.config.ts`, #35). `app` takes the jsdom tests under `src/` on the `vmForks` pool, which reuses each worker across files. `scripts` takes `scripts/` on `forks`, because vite's `runnerImport` fails inside a vm. Pick one with `--project app` or `--project scripts`. In `app`:
- a test file shares its worker with the files before it, so restore every stub (`vi.stubEnv`, `vi.stubGlobal`, the TZ) in `afterEach` or `afterAll`;
- `fetch` and the JSON it parses come from Node's realm, so compare fetched data with `toEqual`, not `toStrictEqual`;
- `src/test/setup.ts` also resets the studio's branch reads, Sets 1 to 8 cards and version batch (#68), and the change history's commit details. Loading them there loads `githubCommit` before a test file's `vi.mock` registers, so studio tests stub `fetch` through the harnesses in `src/tools/studio/finishes/__tests__/` instead of mocking it.

## Updating the app pin

1. `git submodule update --remote upstream/inkweave` (it moves the pin, so a hook requires the owner's approval and the `USER_APPROVED=1` prefix)
2. `pnpm check:deps --fix` then `pnpm install`
3. `pnpm typecheck`, `pnpm test:run`, `pnpm build`
4. On a branch, commit `chore: bump upstream/inkweave to <short sha>` and open a PR.

Dependabot opens these PRs weekly. CI on them is the bridge's contract test.

## Hosting and security (non-negotiable)

- The Vercel project `inkweave-admin` is deployed only by `.github/workflows/deploy.yml` (`vercel deploy --prebuilt`). It has no Git connection. If one is added again, `vercel.json` still keeps Git-triggered deployments off (`git.deploymentEnabled: false`). **Never install or run the Vercel CLI locally** (a cold install crashed this machine twice).
- **Deployment Protection stays on All Deployments.** Standard Protection leaves production domains public, `inkweave-admin.vercel.app` included (#7). Every deploy refuses to ship unless the project uses All Deployments (`scripts/vercel-project-urls.mjs`). It then fails if the new deployment, `ADMIN_PRODUCTION_URL` or any of the project's domains answers an anonymous request (`scripts/assert-login-gate.mjs`).
- **Never add a custom domain.** Admin doesn't need one, and every production domain would become public if protection ever dropped back to Standard.
- Secrets live in GitHub Actions secrets (plus Dependabot secrets for `APP_REPO_TOKEN`). The owner sets token values; never type a token.
- `VERCEL_TOKEN` has team scope (All Projects) and is shared with the app repo's deploy, because `vercel pull` rejects project-only tokens. Rotate it in both repos together.
- `forwarded-paths.json` is the single list of app paths forwarded to inkweave.ink. The Vite proxy reads it; `vercel.json` must match, and a test enforces that.
- Admin's own generated data lives under `/admin-data/`, never `/data/`, which is forwarded to the app.

## Environment

- Windows 11, Windows PowerShell 5.1 (no pwsh 7; no `&&`), Git Bash available.
- The origin remote uses the SSH alias `github-personal`. The submodule URL is relative (`../inkweave.git`), so it follows the alias locally and uses HTTPS in Actions.
- Node 24, pnpm 10 (10.34.7, pinned in `package.json`). pnpm runs no dependency install scripts: an install that meets a new one fails (`strictDepBuilds`) until `pnpm-workspace.yaml` lists it under `allowBuilds`, `true` to run it or `false` to skip it.

## Git workflow

- Branches are `feature/<issue>-<desc>` or `fix/<issue>-<desc>`. Commit messages are semantic and include the issue reference.
- Commit and push only after the owner explicitly approves, with `USER_APPROVED=1` as the literal first characters of the command. Never pipe a commit or a push. Run them with the Bash tool: the hooks also watch PowerShell, which cannot carry the prefix, so a commit or push there is always blocked.
- Gates: `.husky` runs lint and tests on commit, and dependency parity plus typecheck on push. `.claude/hooks` provides git safety, the branch check and read-only `upstream/` (file edits, and git writes run there from Bash or PowerShell). When you change a hook, add cases to `scripts/check-hooks.mjs` and run `pnpm check:hooks`.

## Code Health (CodeScene)

- After changing code, run CodeScene's `code_health_review` on the changed files. If Code Health drops, fix it, review again, and confirm with `code_health_score`. Before a commit, run `pre_commit_code_health_safeguard` and stop only when it passes. Before a PR, run `analyze_change_set` against `main`.
- The PR's CodeScene check is stricter than the local tool: it failed R1 and R2 on files the local tool passed. Keep new code at 10: cyclomatic complexity 8 or less per function, at most 4 arguments, and under 30% primitive arguments per module (`string`, `number`, `boolean` and their aliases, such as `Day`).
